### **开源框架对比表**

该表深入分析LeRobot、StarVLA和RLinf这三个代表性的开源系统，并详细列出它们各自满足了哪些需求，以及满足的程度。  
这三个系统在具身智能的研发生态中扮演着互补的角色，各自的侧重点不同：

* **LeRobot**: 专注于**标准化、易用性和部署**。它致力于降低具身智能的入门门槛，打通从数据到真实机器人的全流程，并与Hugging Face生态深度融合，强调社区协作和成果共享。  
* **StarVLA**: 专注于**算法的快速原型验证和模块化**。它提供了一个“乐高式”的灵活框架，让研究人员可以轻松地组合和测试不同的VLA模型架构与训练策略。  
* **RLinf**: 专注于**大规模训练的系统性能优化**。它是一个底层的、高性能的分布式训练框架，旨在解决在线强化学习中“仿真-推理-训练”流程的效率瓶颈，追求极致的硬件利用率和训练吞吐量。

### **总结与互补关系**

* **LeRobot** 是一个\*\*“全能型选手”**，覆盖了从数据到部署的完整流程，尤其在**数据标准化**和**硬件部署\*\*这两个“始”和“终”的环节做得最好。它最适合那些希望快速上手、复现SOTA结果并将其部署到真实机器人上的开发者和团队。  
* **StarVLA** 是一个\*\*“算法研究员的利器”**，它在**模型训练**阶段提供了无与伦比的**灵活性和模块化\*\*。它最适合那些专注于探索和创新VLA模型架构、损失函数或训练策略的学术研究人员。但它的灵活性也是构建在Huggingface的transformers之上的, 而且目前仅针对Qwen相关模型有自己的实现.  
* **RLinf** 是一个\*\*“高性能计算引擎”**，它专注于解决**模型训练**阶段中最困难、最耗费资源的**大规模在线RL的系统效率问题\*\*。它本身不是一个完整的VLA研发框架，而是构建这样一个框架所需的最强劲的“动力心脏”。一个追求极致性能的团队，可能会用RLinf作为底层基础设施，在其上构建类似StarVLA的算法层和类似LeRobot的部署层。

### **选型与计划**
综上所述，个人认为 StarVLA 虽然号称可以像乐高那样构建模型, 但支持的模型类型中没包含世界模型, 也不支持 RL, 仅对Qwen为基础的模型支持较好. 而另一方面, StarVLA 的灵活性是构建在 Huggingface 的 transformers 上的, 也就是说, 我们用 Huggingface 的 LeRobot 也可以实现类似的灵活性, 虽然可能代码量会比 StarVLA 多点, 但 LeRobot 对具身智能的支持会多很多, 而且在AI编程的加持下, 代码量大并不是个很大的问题. 如果引入了对StarVLA的支持, 后续需要多接入与维护一个开源框架, 容易发生兼容问题.

而 RLinf 虽然对具身智能支持的范围没有 LeRobot 大, 但它对 RL 和分布式计算的支持十分深入, 能弥补 LeRobot 对 RL 支持较弱,且不支持真机RL和online RL的缺点.

因此, 我们的**选型结果**是 LeRobot 和 RLInf.

### 3.3 StarVLA 分析与排除理由

#### 3.3.1 技术概述

StarVLA 采用"分层配置 + 工厂注册"的乐高式设计，允许研究人员灵活组合视觉编码器、语言模型、动作头等组件来构建 VLA 模型。其灵活性建立在 Hugging Face transformers 库之上。

#### 3.3.2 排除理由

**理由一：模型覆盖范围有限**

StarVLA 目前仅对 Qwen 系模型有成熟实现。不支持世界模型训练，不支持 RL 训练。在团队最需要的两个关键能力（灵活模型架构 + RL 训练）中，StarVLA 只能部分满足前者，完全无法满足后者。

**理由二：灵活性可被 LeRobot 替代**

StarVLA 的"乐高式灵活性"建立在 HF transformers 之上。LeRobot 同样基于 HF 生态，通过 `PreTrainedPolicy` + `ProcessorPipeline` 的抽象，也能实现灵活的模型架构定制。虽然 LeRobot 上实现同样的灵活性可能需要更多代码，但在 AI 辅助编程的加持下，代码量差异不再是关键障碍。

**理由三：引入第三框架增加维护成本**

维护三个开源框架（LeRobot + StarVLA + RLinf）的成本远高于两个（LeRobot + RLinf）：
- 三个框架的 API 变更都需要跟进
- 框架间的兼容性测试面积增加
- 团队需要同时掌握三套不同的设计理念和代码风格
- 版本升级时的冲突风险更高

**理由四：功能重叠大于互补**

StarVLA 与 LeRobot 在 IL/SFT 训练阶段有大量功能重叠：
- 两者都支持基于 HF transformers 的模型构建
- 两者都支持标准的 SFT 训练流程
- 两者都支持视觉数据增强
- StarVLA 不提供 LeRobot 缺失的关键能力（RL、真机部署、数据标准化）

相比之下，RLinf 与 LeRobot 几乎没有功能重叠，是真正的互补关系。

**理由五：社区与生态风险**

StarVLA 是大学实验室驱动的项目，社区规模和维护团队远小于 Hugging Face 支撑的 LeRobot。长期来看，依赖小型社区项目的风险更高（维护停滞、API 断裂、文档缺失等）。


**StarVLA 排除理由**：
- 与 LeRobot 功能重叠大，互补性弱
- 完全不提供 RL 能力——团队最关键的需求
- 模型覆盖仅限 Qwen 系
- 引入第三框架增加 +50% 维护成本和 +200% 兼容性测试面积
- 灵活性可在 LeRobot 上以更多代码实现
